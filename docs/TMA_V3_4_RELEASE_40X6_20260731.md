# Ventus TMA V3.4：40+6 解耦后端与面积清理

## 当前结论

V3.4 的 RTL、GVM、功能、周期和结构门槛已经通过，最终配置确定为：

```text
1 ActiveCommand + 1 LookaheadSlot
40 LineContext + 6 PayloadSlot
4-entry compiled TensorMap store
```

没有采用 40+8：最终 40+6 在全部冻结周期点上均不慢于 V3.3，且乱序/背压
测试已经让 40 个 LineContext 和 6 个 PayloadSlot 全部占满并正确恢复。
V3.4 相对 V3.3 的改动局限于 TMA 实现、TMA 测试、生成 RTL 和测试/综合
脚本；L2、shared memory、TLB 外部接口、调度器、ISA 与 TensorMap
内存格式没有改变。

40+8 探针是在最终 S2G recycling 修复前运行的，只用于判断“额外 payload
是否能消除当时的阻塞”。它在 4/8/16/32 KiB S2G 上分别为
209/305/499/883 cycles，均慢于最终 40+6 的 196/296/488/874；更关键的
是最终 40+6 已没有任何 V3.3 回退。因此“40+6 因 payloadFull 回退且
40+8 消除回退”的采用条件不成立。

正式 baseline 尚未创建，`CURRENT_VERSION` 也尚未更新。原因是唯一一次
N12 DC 尚在运行；映射面积和 1.5 GHz 时序是最后的发布门槛，而不是用
RTL 状态位估算替代。

## 数据通路

```text
data command --> Lookahead(validate/descriptor/bind/reserve)
                                   |
                                   v
                            ActiveCommand
                                   |
                     compact 3-stage Planner
                                   |
                          WindowDecomposer
                                   |
              +--------------------+--------------------+
              |                                         |
        G2S LineContext                            S2G PayloadSlot
        TLB/L2 request                             shared/transform
              |                                         |
        L2 response                                 L2 write + ack
              |                                         |
        PayloadSlot/transform                       release payload
              |
        shared request/ack
```

40 个 LineContext 只保存 line tag、PPN 和紧凑 route，不保存 1024-bit
payload。6 个 PayloadSlot 是 TMA 内唯一可驻留的 128B 数据阵列。G2S
在 response 到达时把 route 和数据原子转入 PayloadSlot并释放
LineContext；S2G 在最后一个 write 被接受时释放 payload，完成信息由
独立 ack valid 表保存。

严格单 active command 使 ASID、方向、codec、fill、reduce、barrier 和
group 都只保存一份。source ID 也按方向复用：G2S 的 `0..39` 直接索引
LineContext，S2G 的 `0..31` 直接索引 write ack，descriptor refill 使用
63。方向只在所有 TMA 内部资源排空后切换。

TensorMap 的显式 prefetch 和普通 Tensor 命令的 demand lookup 共用同一个
4-entry compiled store。Lookahead 可以在当前数据命令执行时完成下一条
命令的 descriptor 查询、编译和绑定，但不会提前启动任何数据搬运。

payload 容量。

| standalone TMA 顺序状态 | 53,543 bit | 28,712 bit | -46.38% |

生成 RTL 中恰好只有 6 份 1024-bit payload。检查未发现：

- 40 路 payload mux、40×40 compare 或 response 广播；
- 大于 1024-bit 的动态移位结果；
- runtime `/`、`%`、divider 或 remainder；
- PMU counter/timestamp/perf output；

- Compiler tag/ASID 与 compiled entry 的重复副本。

目前剩余的大项是 40×240=9,600 bit 的 LineContext 和
6×1,465=8,790 bit 的 PayloadSlot。二者都在压力测试中达到满占用：
继续减少 entry 会直接降低可覆盖的 L2 延迟或 shared 突发背压，而不是
删除“永远无效”的空间。下一轮显著面积优化应优先根据 DC hierarchy
处理组合网络和标准单元映射，不应盲目再砍这两个池。

### 映射面积变化

V3.4 并没有比 V3.3 增大。总面积减少 83,671.94，组合和顺序面积均
显著下降：

| 顶层项目 | V3.3 | V3.4 | 变化 |
|---|---:|---:|---:|
| combinational area | 135,795.19 | 77,731.70 | -42.76% |
| noncombinational area | 50,245.66 | 24,637.22 | -50.97% |
| total cell area | 186,040.85 | 102,368.92 | -44.98% |
| combinational cells | 461,051 | 309,461 | -32.88% |
| sequential cells | 50,341 | 27,181 | -46.01% |

WindowEngine 从 145,388.86 降到 64,656.97，是总面积下降的主要来源。
它的组合面积减少 60,249.74，顺序面积减少 20,482.14。40+6 拆分确实
解决了 V3.3 宽 TransferSlot 的面积问题。

局部仍有三项面积增加：

| 位置 | V3.3 | V3.4 | 增量 |
|---|---:|---:|---:|
| WindowPlanner local combinational | 17,917.25 | 20,124.39 | +2,207.14 |
| Descriptor Service local combinational | 1,501.55 | 2,013.57 | +512.02 |
| 顶层 glue local combinational | 14.00 | 352.05 | +338.05 |

Planner 总面积仍下降 1,218.97，因为队列寄存器减少 3,426.11；但宽状态
压缩把更多工作变成了同周期组合运算。Descriptor Service 总面积也仍
下降 232.24，局部组合增长被 Compiler/存储状态下降抵消。

如果“之前”指更早的 56,133.91 基线，则 V3.4 仍然大 46,235.01
（82.37%）：

| 顶层项目 | 旧 V2 | V3.4 | 增量 |
|---|---:|---:|---:|
| combinational area | 37,080.06 | 77,731.70 | +40,651.63 |
| noncombinational area | 19,053.84 | 24,637.22 | +5,583.38 |
| total cell area | 56,133.91 | 102,368.92 | +46,235.01 |

这个差值几乎全部是组合逻辑，而不是40+6寄存器本身。旧 V2 只有4个
line entry、2个 descriptor、64B shared bundle、固定128B任务加16B
fallback，并未实现当前完整的8-lane 5D Planner和通用乱序后端。
此外旧报告使用 `tt0p8v25c`、1600MHz综合/1500MHz重报，V3.4使用
`tt1v85c`、1500MHz，因此这不是严格 matched-corner面积门槛。

即便带着这个限制，运算器差异仍很明确：V3.4相对旧 V2 的
`DW_rightsh` 增加约16,172 area、adder增加约5,494、comparator增加
约3,279、`DW_leftsh`增加约2,684，另增加一个约1,710 area的乘法器。
这些项目合计解释了大部分新增组合面积。要接近旧56K，单纯把
descriptor从4项改2项或再少几个buffer远远不够，必须重构 Planner
算术和 LinePermuter。

DesignWare 估算揭示了最明显的组合问题：

| 运算器 | V3.3 | V3.4 | 增量 |
|---|---:|---:|---:|
| `DW_rightsh` | 7,406.19 | 16,390.90 | +8,984.71 |
| `DW_leftsh` | 11,193.99 | 2,739.94 | -8,454.04 |
| `DW_cmp` | 4,163.31 | 3,820.43 | -342.88 |
| `DW_mult_uns` | 1,759.75 | 1,709.89 | -49.86 |

V3.4 将双向移位统一为源码中的一个表达式，但该表达式位于8-lane循环内。
生成 RTL 实际包含 `permuterShifted` 到 `permuterShifted_7` 共8个
1024-bit动态右移器。因此共享的是一个 payload array 读选择点，并不是
一套物理移位器。这8个宽 barrel shifter 是当前首要的可减少组合面积。

模块面积 CSV 按下面的逻辑层次排列：

```text
tma
├── TmaV3Ingress
│   ├── TmaV2CommandBinder
│   └── TmaV2WindowPlanner
└── TmaV2WindowSubsystem
    ├── TmaV2DescriptorService
    │   └── TmaV2DescriptorCompiler
    └── TmaV2WindowEngine
```

其中 `hierarchical_total` 是**包含全部后代**的层次总面积，
`self_comb/self_seq/self_total` 才是该模块壳自身、不含子模块的面积。
所以父项和子项不能再次横向相加。例如 V3.4：

`TmaV2WindowSubsystem 72,088.1867 =
self 0 + DescriptorService 7,431.2123 + WindowEngine 64,656.9745`。

同理，`DescriptorService` 的总面积已经包含 `DescriptorCompiler`；
`WindowPlanner` 则属于 `Ingress`，不是 `WindowSubsystem` 的子项。
CSV 中的 `direct_children`、`parent_logical_path` 和
`reconstruction_error` 列分别明确记录父子关系及加总校验。V3.3 比
V3.4 多一层纯包装 `TmaV2DmaCore`，其 local area 在 CSV 顶层 `tma`
行中折入 `self_total`，从而使两版的逻辑层次可直接比较。

### 时序根因

V3.4 的逻辑级数从70降到51，TNS从 -7417.39 改善到 -3595.29，
violating paths 从44,333降到24,511；但 WNS 仍为 -0.2268 ns。报告的
100条最差路径全部起止于 WindowPlanner。

最差 endpoint 是 `globalStage` 中 lane 7 的 `globalBytes`。对应 RTL
先为每 lane/每 byte 做16次坐标加法和边界比较，形成16-bit mask，然后
再做 `PriorityEncoder + PopCount` 重新编码成 offset+length。也就是说
V3.4 虽然在 stage 间只保存紧凑字段，生成它们时仍支付了完整 mask
展开和回收的组合成本。这同时解释 Planner 组合面积增长和 WNS 未改善。

### 下一轮优化顺序

1. **把 Planner OOB 改成区间算法。** 直接根据
   `coordinate0/globalDim0/payloadBytes/dtype` 求合法 byte
   `offset+length`，删除8×16逐 byte compare、mask、PriorityEncoder
   和 PopCount。普通 8/16/32/64-bit dtype用 clamp和移位；packed FP4
   用加1后右移；padded FP4/FP6保留 all-or-none 判断。该改动不增加
   pipeline stage，最可能同时降低约2K级 Planner组合面积并改善 WNS。
2. **把8×1024-bit barrel shift改成 atom-pair permuter。** 先用
   `offset[6:4]` 在8个128-bit atom中选择相邻两个，再只对256-bit窗口
   使用 `offset[3:0]` 做 byte realignment。G2S extract和S2G insert
   共用相同的两级网络，仍可每周期处理一个128B response，不是布局
   fast path。目标是把16,390.90的右移器面积降低约一半以上。
3. **压缩 Cursor token。** GlobalMap 实际只需要每 lane 的
   `coordinate0 + outerInBounds + componentSum + row`，不需要保存5个
   32-bit coordinate。把外层4维比较结果在 CursorExpand 中压成1 bit，
   可从 Cursor queue 再删约1,016个状态位；需用 module-level DC确认
   没有把关键路径搬到 cursor recurrence。
4. **重构 cursor address recurrence。** 当前保存5×64-bit
   `cursorComponent` 并对每 lane 做5项求和。可由 Binder 计算命令级
   advance/wrap delta，Planner只维护一个64-bit累计 global offset。
   这比把 `stepOffsets` 重新放回4项 descriptor cache更合理，因为只在
   单 active command中保存一份。
5. **最后才考虑容量。** 4-entry descriptor降到2-entry的独立 DC
   实测可省约2,057 area，约占当前 TMA 2%；但会损失交替 TensorMap
   复用。40 LineContext和6 PayloadSlot均在压力测试中满占用，不应作为
   第一轮削减对象。

前两项预计收益最大，而且第一项直接针对时序失败。应先做独立
WindowPlanner/LinePermuter RTL与短 DC，确认组合面积和 WNS，再合入下一
个完整版本；不应立即启动第二个全 TMA DC。
